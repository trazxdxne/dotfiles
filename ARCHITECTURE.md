# Архитектурный проект: Рефакторинг Dotfiles и Rust Установщик

## 1. Аудит репозитория и очистка (Repository Audit & Cleanup)

### Анализ текущей структуры
Текущий репозиторий представляет собой плоскую структуру, где смешаны пользовательские конфигурации (например, `wezterm`, `hypr`, `niri`), системные переопределения, требующие прав root (`polkit-1`, `modprobe.d`, `edid`), скрипты (`scripts`), а также инфраструктурные решения и бинарные артефакты (`obsidian-livesync`, `ly.tar.gz`).

### Антипаттерны, подлежащие устранению
1. **Бинарные артефакты и архивы:** Файл `ly.tar.gz` должен быть удален. Хранение архивов в Git-репозитории dotfiles нецелесообразно. Если это исходники для сборки, они должны скачиваться скриптом или управляться через пакетный менеджер.
2. **Инфраструктура в Dotfiles (IaC):** Директории `obsidian-livesync` (содержащая `docker-compose` и стейт базы данных CouchDB) и `tailscale` концептуально не являются dotfiles. Это инфраструктура (Infrastructure as Code - IaC). Они должны быть выделены в отдельную сущность или репозиторий.
3. **Отсутствие разделения прав (Permissions Mixing):** Конфигурации для `$HOME/.config` лежат в корне вместе с файлами для `/etc/` (например, `polkit-1`). Это усложняет автоматизацию установки и понимание, какие права требуются для симлинков или копирования.

### Строгие правила очистки
- **Удалить:** `ly.tar.gz` и любые другие локальные дампы состояний.
- **Изолировать (Extract to IaC):** Создать папку `iac/` (или вынести в отдельный репозиторий) для `obsidian-livesync` и специфичных сетевых конфигов (`tailscale`).

## 2. Доменно-ориентированная реструктуризация (Domain-Driven Restructuring)

Новая структура будет строго модульной, разделяя конфигурации по доменам применения и требуемым привилегиям.

```text
.
├── config/              # [Домен: Пользовательские конфиги] Symlinks in ~/.config/
│   ├── niri/
│   ├── wezterm/
│   ├── fastfetch/
│   └── ...
├── system/              # [Домен: Системные переопределения] Files in /etc/ or /usr/ (Root required)
│   ├── polkit/          # /etc/polkit-1/rules.d/
│   ├── modprobe/        # /etc/modprobe.d/
│   ├── edid/            # /usr/lib/firmware/edid/
│   └── pam/             # /etc/pam.d/
├── themes/              # [Домен: Оформление] GTK, Qt, Icons, Cursors
│   ├── gtk-3.0/
│   ├── gtk-4.0/
│   ├── qt5ct/
│   └── qt6ct/
├── scripts/             # [Домен: Исполняемые скрипты] Symlinks in ~/.local/bin/
├── iac/                 # [Домен: Инфраструктура] Docker, CouchDB, Tailscale
│   └── obsidian-livesync/
├── knowledge/           # Документация и инструкции
└── installer/           # [Домен: Инструментарий] Rust CLI Установщик
```

## 3. Архитектура Rust Установщика (Rust CLI Installer Architecture)

Установщик будет написан на Rust. Интерфейс будет реализован в виде интерактивного CLI (с использованием `inquire` для опросов и `indicatif` для отображения прогресса).

### State Machine Установщика
1. **Initialization:** Проверка окружения (ОС, наличие `git`, базовые зависимости).
2. **Module Selection:** Парсинг доступных модулей из структуры директорий. Использование `inquire::MultiSelect` для выбора пользователем (например, "Окружение Niri", "Терминал", "Аудио", "Инфраструктура").
3. **Queue Generation:** Построение ориентированного ациклического графа (DAG) зависимостей. Например, применение темы GTK требует установки пакетов.
4. **Execution & Batching:** Выполнение сгенерированной очереди.

### Решение проблемы "pkexec spam" (Root Context Batching)
Главное ограничение — избежать многократных запросов пароля sudo (`pkexec`).
**Решение:** Разделение графа задач на "Пользовательский контекст" и "Контекст суперпользователя (Root)".
Установщик соберет все необходимые root-операции (копирование файлов в `/etc/`, вызовы пакетного менеджера для установки системных пакетов, патчинг системных конфигов) в единый `Bash`-скрипт (или структурированный JSON-файл задач) во временной директории, а затем **один раз** запустит вспомогательный бинарник (или сам себя с флагом `--root-worker`) через `pkexec`.
Таким образом, пароль запрашивается ровно один раз.

## 4. AST-Уровень: Механизм синтаксического патчинга (AST-Level Syntactic Patching Engine)

Слепое перезаписывание файлов (например, `/etc/ly/config.ini` или `/etc/pam.d/ly`) ломает систему при обновлениях дистрибутива.

### Механизм автоматического патчинга
1. **Резервное копирование (Rollback & Backup):** Перед любой модификацией система создает копию с суффиксом, включающим timestamp: `filename.ext.bak_20231027_153000`. При сбое в рамках одной сессии будет выполнен автоматический rollback к этим `.bak` файлам.
2. **AST-Парсинг для TOML (crate `toml_edit`):** Для файлов конфигураций, таких как `greetd/config.toml` (если применимо), будет использоваться `toml_edit`. Он позволяет изменять значения ключей, сохраняя форматирование и комментарии оригинального файла.
3. **Regex и Маркерный патчинг для нестандартных форматов (crate `regex`):** Для `.conf`, `.ini` (если нет надежного парсера с сохранением форматирования), `.lua` и `pam` файлов будет использоваться построчное чтение и замена с помощью RegEx.
   - Логика будет искать ключи (например, `Inherits=` в `index.theme` или строки в `/etc/pam.d/ly`).
   - Если нужный блок или строка не найдены, они будут добавлены (желательно в конец блока).

## 5. Интеграция унаследованных команд (Legacy Command Integration)

Шаги из `Environment_Setup.md` будут преобразованы в код следующим образом:

### Пакетный менеджер
В Rust будет определен трейт `PackageManager`:
```rust
trait PackageManager {
    fn install(&self, packages: &[&str]) -> CommandResult;
    fn check_installed(&self, package: &str) -> bool;
}
```
Реализация `PacmanYay` будет использовать `yay -S --noconfirm` для пользовательских пакетов и `pacman -S --noconfirm` внутри сгенерированного root-контекста.

### Управление сервисами (Systemd)
Запуск и добавление в автозапуск демонов (например, `systemctl enable --now lock-on-sleep.service`) будет реализовано через функцию-обертку, вызывающую `systemctl` с нужным контекстом (`--user` или на уровне системы внутри root-worker).

### Настройка MIME-типов и GSettings
Вместо ручного ввода команд `xdg-mime default` и `gsettings set`, установщик будет считывать декларативный список настроек (например, из JSON/YAML) и применять их через вызовы `std::process::Command`.

### Интеграция Инфраструктуры (Docker, CouchDB)
Шаги настройки Obsidian LiveSync (Docker) будут выделены в отдельный модуль выбора. Если пользователь его выбирает:
1. Устанавливаются пакеты `docker`, `docker-compose`.
2. В root-контексте запускается и добавляется в автозагрузку демон `docker`.
3. Установщик запросит (через `inquire::Password`) учетные данные для CouchDB, сгенерирует `.env` файл и выполнит скрипты инициализации (через HTTP API CouchDB или `curl`).
